# WF-0012 — Alembic Migration Baseline PRD

Artifact: prd  
Version: v0.2  
Status: Ready for Tasks  
Last Updated: 2026-02-16

## 1. In Scope

- Initialize Alembic for backend Postgres workflow under `backend/`.
- Configure Alembic environment to load project SQLModel metadata.
- Add first baseline migration revision representing current schema using `alembic revision --autogenerate`, followed by manual review before apply.
- Update backend docs/runbook with exact migration lifecycle commands.
- Verify migration command flow for current/history/upgrade/downgrade/re-upgrade.

## 2. Out of Scope

- SQLite migration support.
- Production deployment automation or CI migration rollout.
- New product features or schema redesign unrelated to baseline setup.
- Advanced zero-downtime migration recipes.

## 3. User / System Flow

### Happy Path

1. Maintainer sets Postgres `DATABASE_URL`.
2. Maintainer runs Alembic command sequence from `backend/`.
3. Alembic resolves metadata and applies baseline migration.
4. Maintainer confirms revision state and history output.
5. Maintainer validates reversible baseline via downgrade then upgrade.

### Failure Path A: Missing or invalid `DATABASE_URL`

- Alembic command fails with connection/config error.
- Runbook directs user to set a valid Postgres URL before retry.

### Failure Path B: Metadata import failure in Alembic env

- Autogenerate or migration command fails because metadata target cannot load.
- Fix module import/target metadata configuration and rerun command.

### Failure Path C: Baseline drift on existing local DB

- Local DB state conflicts with baseline assumptions.
- Runbook provides reset/stamp path for local-only environments, then retry.

## 4. Functional Requirements

1. Alembic scaffold exists in backend repository and is source-controlled.
2. Alembic config reads Postgres URL from project environment contract.
3. `env.py` points to project SQLModel metadata used by runtime models.
4. Baseline revision file exists as root (`down_revision = None`).
5. Baseline migration is immutable once committed; any follow-up schema changes must be new revisions.
6. Local drift handling is documented with explicit recovery paths (`reset local DB` or `alembic stamp`) for non-production environments.
7. Commands below succeed on local Postgres dev path:
   - `uv run alembic current`
   - `uv run alembic history --verbose`
   - `uv run alembic upgrade head`
   - `uv run alembic downgrade -1`
   - `uv run alembic upgrade head`
8. Documentation updates include command purpose, expected output shape, and failure handling notes.
9. Documentation explicitly states this WF does not automate production migration rollout.

## 5. Data & API Contracts

### Input Contract

- Required env var: `DATABASE_URL` with Postgres connection string.
- Runtime assumption: backend SQLModel model modules are importable by Alembic env.

### Command Contract

- Migration commands execute from `backend/` using `uv run alembic ...`.
- `upgrade head` transitions to latest revision.
- `downgrade -1` transitions one revision backward.
- `current` and `history --verbose` provide revision observability.
- Baseline generation command is run once for this WF and reviewed before apply.

### State Transitions

- `uninitialized` -> `baseline_at_head` (after first `upgrade head`)
- `baseline_at_head` -> `pre_baseline` (after `downgrade -1`)
- `pre_baseline` -> `baseline_at_head` (after re-upgrade)

## 6. Components / Modules

- `backend/alembic.ini`
  - Alembic runtime configuration.
- `backend/migrations/env.py`
  - DB URL and metadata binding for migrations.
- `backend/migrations/versions/<revision>_baseline.py`
  - Baseline schema revision.
- `backend/README.md` (or existing backend runbook doc)
  - Operator-facing migration commands and troubleshooting notes.

## 7. Edge Cases

- Async DB URL compatibility in Alembic context may require normalization.
- Autogenerated baseline may include ordering/default artifacts that require manual review.
- Existing developer DBs may not match baseline assumptions and need local reset/stamp guidance.

## 8. Telemetry (Minimal)

- Use Alembic command output and revision IDs as operational trace for migration actions.
- No new application telemetry or analytics instrumentation in this WF.

## Deferred / Not in MVP

- Automated migration checks in CI pipelines.
- Multi-environment release sequencing playbooks.
- Data backfill automation patterns and concurrent index policies.
- Any migration changes beyond the first baseline revision.
